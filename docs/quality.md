# 개발·검토 기준

제품 계약은 [요구사항](requirements.md), 구조는 [상세설계](lld.md), 디자인은 [디자인 기준](design.md), OS·SDK 변경은 [호환성](compatibility.md)을 따른다. 이 문서는 반복 가능한 검토 방법이고 [QA 기록](qa.md)은 실제 수행 결과다. 기준을 적었다는 이유로 검증 완료로 보고하지 않는다.

## 작업 순서와 완료 조건

1. Git 상태와 적용 문서를 읽고 기존 변경을 보존한다. 변경의 사용자 효과, 상태·저장 계약과 검증 범위를 정한다.
2. UI·플랫폼 API 변경은 해당 영역의 **현재 Apple 공식 문서**를 확인한다. 출처, 확인 날짜, 적용 결정과 예외를 기록한다. 제3자 스킬은 보조 자료이며 공식 문서와 구분한다.
3. 논리 단위로 구현하고 관련 테스트를 실행한다. 데이터·취소·상태 전이 회귀는 의미 있는 테스트로 남긴다. 저위험 문구 수정이나 구현을 반복하는 테스트는 추가하지 않는다.
4. 코드 변경은 `./scripts/check.sh`를 통과한다. 기능·UI·성능 변화는 아래 해당 검토를 추가한다. 실패를 숨기거나 린트 전체 비활성화·임의 baseline으로 해결하지 않는다.
5. 결과를 날짜·소스 revision·앱 바이너리·도구·OS·조건·수행 범위·미확인 사항과 함께 기록하고 관련 문서를 갱신한다. 커밋은 AGENTS.md의 한국어 Conventional Commits를 따른다.

## 자동 검사와 코드 규칙

```sh
./scripts/format.sh
./scripts/check.sh
```

`format.sh`는 소스만 포맷한다. `check.sh`는 포맷 strict 검사, 고정 버전 SwiftLint, 구조·문서 링크·스크린샷 해시 확인, Swift Testing, Release 패키징·서명 검증을 수행한다. 도구와 SDK, 테스트·빌드 로그는 Git에서 제외한 `work/quality/`에 남긴다. 앱 실행이나 실제 AI 호출, HIG 적합성·교재 사실성·체감 성능은 이 명령의 합격 항목이 아니다.

- swift-format: 4칸, 목표 100열, 문자열 원문 보존. 도구는 선택한 Swift toolchain을 사용하므로 버전 변경은 포맷 diff를 별도 검토한다. 전체 포맷 변경을 기능 수정과 섞지 않는다.
- SwiftLint 0.65.1: 공식 portable 배포의 SHA-256을 확인한 뒤 `.tools/`에만 설치한다. 앱 런타임 의존성은 추가하지 않는다. 중복 import, 강제 cast/try, 사용하지 않는 closure·optional binding 등 선택한 규칙을 strict로 검사한다. 스타일 규칙은 포맷터와 중복시키지 않는다.
- 규칙 예외는 가장 좁은 범위에서 이유를 남긴다. 강제 unwrap·`@unchecked Sendable`은 불변 조건과 동기화 근거를 코드에 적고 위험 경로를 테스트한다. 파일 길이만 맞추기 위한 무의미한 분리는 하지 않는다.
- UI 상태는 메인 액터에서 다룬다. 무거운 연산·프로세스 대기·빈번한 디스크 쓰기를 UI 이벤트마다 수행하지 않는다. WebKit/AppKit의 메인 액터 요구와 파일 저장 순서를 보존하며 작업을 옮긴다.
- 사용자에게 표시할 오류는 구체적인 실패와 복구 동작을 설명한다. 인증·프롬프트·교재·메모를 공개 로그에 남기지 않는다.

선택한 CI는 macOS 26 / Xcode 26.6이며 자동 검사와 **고정 샘플의 로컬 그림·PDF QA**를 실행한다. 새 OS에 대한 실제 실행 검증은 별도 기록한다. CI 환경을 바꿀 때 [GitHub 공식 runner 이미지](https://github.com/actions/runner-images/blob/main/images/macos/macos-26-arm64-Readme.md)의 제공 버전을 다시 확인한다.

도구 근거: [swift-format](https://github.com/swiftlang/swift-format), [SwiftLint](https://github.com/realm/SwiftLint), [SourceKitten 도구 경로 탐색](https://github.com/jpsim/SourceKitten/blob/main/Source/SourceKittenFramework/library_wrapper.swift). CLT에서는 활성 swiftc의 toolchain 경로를 린트 프로세스에만 전달한다. 전역 xcode-select나 사용자 환경을 바꾸지 않는다.

## 실제 화면 검토

UI 변화가 있을 때 관련 화면을 앱에서 조작한다. macOS 앱은 시뮬레이터 화면으로 대체하지 않는다.

- 기본 18pt와 최대 36pt, 넓은 창과 최소 창 폭, 밝게·어둡게·시스템 테마를 확인한다.
- 사이드바·툴바·본문 경계, 줄·여백·선 정렬, 긴 제목·설명·빈 상태·로딩·실패·완료 상태를 확인한다.
- 명령의 기능 이름·상태·메뉴·단축키가 일치하고 사용자가 다음 동작을 찾을 수 있는지 확인한다.
- 본문과 하단 조작 영역이 겹치지 않고 표·코드·ASCII의 원래 줄·공백이 보존되는지 확인한다.
- 키보드 이동, VoiceOver 이름·순서, 대비 증가·투명도 감소·동작 감소 설정을 변경 영역에서 확인한다. 설정별 미실행을 명시한다.
- 기본 시스템 컴포넌트를 먼저 선택한다. Glass는 탐색·조작 층에 절제해 사용하며 읽기 본문·표·그림을 가리지 않는다. OS의 디자인 변화에 임의 픽셀 보정이나 비공개 API로 대응하지 않는다.

## 생성·저장·PDF 검토

생성 계약·스키마·프롬프트·후처리가 바뀌면 격리된 `--data-dir`에서 실제 계획과 교재 생성을 수행하고 호출 횟수를 기록한다. 로컬 샘플과 실패 fixture, 실제 모델 출력, 생성 후 수정한 QA 사본을 구분한다. 저장된 자료나 로컬 렌더러만 바뀐 경우 같은 자료를 재사용하고 불필요한 재생성을 하지 않는다.

확인 흐름은 주제 입력 → 계획 수정·시작 → 교재·그림 → 퀴즈 메모·선택 정답 공개 → 파트 완료 → 종료·재실행 → PDF다. 실패·취소·시간 제한·손상 파일에서 원본 보존과 복구 경로도 변경 범위에 맞게 확인한다.

JSON 구조 검증 외에 출처·핵심 설명·예제·정답의 일관성과 그림의 글자·방향·사례 이름·캡션의 대응을 검토한다. 표·코드·ASCII의 줄바꿈과 전체 PDF 페이지를 실제로 읽는다. 문제와 해설의 페이지 분리를 확인한다. 자동 검사로 모든 사실이나 표시된 학습 시간을 보증했다고 주장하지 않는다.

## 성능 검토

성능 관련 변경이나 지연 보고가 있으면 재현 자료·기기·OS·Release 바이너리·창·글자 크기·입력 방식을 고정한다. 스크롤, 내용 전환, 큰 그림, 계획 편집, 대규모 보관함 등 문제가 발생한 흐름의 전후를 비교한다.

Instruments의 SwiftUI, Time Profiler, Hangs/Hitches로 메인 스레드 시간, 긴 view body/representable 갱신, 갱신 빈도, 디스크 작업과 끊김을 확인한다. 60/120Hz의 서로 다른 frame deadline을 고려하며 측정 기반 baseline을 정한다. 임의 목표 숫자나 저장 횟수만으로 ‘버벅임 해결’을 판정하지 않는다. trace, 조건, 결과와 재측정 가능한 절차를 QA 기록에 남긴다. 원격 생성 시간과 로컬 UI 지연도 구분한다.

근거: [Apple SwiftUI 성능 분석](https://developer.apple.com/videos/play/wwdc2025/306/). 현재 저장 횟수 개선은 검증했지만 FPS·긴 트랙패드 스크롤 baseline은 미측정이다. 앞으로 성능 변경의 완료 조건에 해당 측정을 넣는다.

## 스크린샷과 배포 기록

UI 변화가 있으면 README의 관련 화면을 다시 캡처한다. 포맷·문서·내부 구조만 바뀌어 화면이 같다면 기존 캡처를 유지한 이유를 QA 기록에 적는다. 실제 앱 PNG를 사용하며 합성 UI나 덧씌운 텍스트를 캡처로 제시하지 않는다.

`docs/assets/screenshots.json`에 캡처 날짜·출처·앱 버전·소스 revision·바이너리 해시·OS·SDK·창·본문 크기·테마와 각 PNG의 SHA-256을 기록한다. 새 캡처는 같은 체크아웃에서 빌드한 앱으로 만들고 불명확한 값은 추정해 채우지 않는다. 해시는 이미지 교체 누락을 검출하며, 현재 UI와의 시각적 일치까지 보증하지 않는다. README에도 캡처 기준을 표시한다. 공개 전 보관함·교재·메모에 개인정보가 없는지 확인한다.
